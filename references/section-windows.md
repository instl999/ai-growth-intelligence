# 分板块时间窗

## 为什么不再统一用 24 小时

新闻类内容和项目类内容的「新鲜」不是一回事。

一条 AI 官方发布，过了一天就不值得再讲。但一个 GitHub 项目或一个 Skill，往往是发布三天、一周之后才真正值得推荐——它发了第一个正式版本、被人用起来、或者只是终于被看见。

过去四个板块共用 24 小时窗口 + 每板块至少 5 条，结果是 `GitHub 精选` 和 `Skill 精选` 经常凑不满 5 条而整块消失；要么就得拿质量不够的仓库凑数。两种结果都不好。

## 现在的规则

| 板块 | 发现窗口 | 性质 |
| --- | --- | --- |
| `AI 情报` | 24 小时 | 新闻，过期就不要 |
| `综合情报` | 24 小时 | 新闻，过期就不要 |
| `GitHub 精选` | 7 天 | 候选池，按今天的动静排序 |
| `Skill 精选` | 7 天 | 候选池，按今天的动静排序 |

候选池板块的排序规则：

1. 24 小时内有新版本、重大更新或首次公开发布的，排在最前面，并在文章里标注「（24 小时内有更新）」。
2. 其余按最近活跃时间倒序。
3. 已经推荐过的直接跳过。
4. 每个板块最多 10 条。

**放宽窗口不等于放低标准。** 来源校验和价值评分一条都没变，窗口只决定「哪些候选有资格被评判」。凑不满 5 条仍然整块省略——宁可少一个板块，也不要注水。

## 判断「新鲜」用哪个时间

条目上有两个时间：

- `occurredAt`：这件事最初发生 / 项目最初出现的时间，必填。
- `lastActivityAt`：最近一次发版或重大更新，选填。

两者取**较晚**的那个，同时决定是否在窗口内、以及排序位置。所以「六天前发布、今早发了 v1.0」的仓库，会被当成今早的新闻处理，排在最前面。

只有候选池板块会显示更新标记。24 小时板块里每条按定义都是新的，标出来只是噪音。

## 去重

已推荐过的条目会被跳过。指纹来自标题和来源 URL，**不含时间**，所以同一个项目发了新版本也不会因为时间变了就重新混进来。

```powershell
# 投递确认之后再记录，否则会白白压制掉没送出去的内容
node src/cli/index.js record-delivered --items items.json
```

`delivery-plan` 会自动读取历史并在返回值里给出 `deduplication.previouslyRecommended` 和 `suppressedThisRun`。加 `--no-history` 可以完全不用本地状态。

记录保留 30 天后过期。永久保留会让一个一年后重新值得一提的项目再也上不了榜。

没有这一步，7 天候选池会让同一个仓库连着推荐一整周——这也是为什么 0.8.0 之前的去重其实是空转：`recordFingerprints` 从来没有被调用过。

## 配置

```json
{
  "sections": {
    "github": { "discoveryWindowHours": 168, "highlightWindowHours": 24, "minItems": 5, "maxItems": 10 },
    "ai":     { "discoveryWindowHours": 24,  "highlightWindowHours": 24, "minItems": 5, "maxItems": 10 }
  },
  "recommendationHistoryDays": 30
}
```

取值会被夹到合理范围（窗口 1 小时到 30 天，条数 1 到 50），`maxItems` 低于 `minItems` 时自动抬到相等，未知板块名会被忽略。只写要改的字段即可，其余沿用默认。

## 用户显式指定周期时

`生成最近 N 小时情报` / `生成本周情报` 会**放宽**所有板块，但不会收窄候选池。请求 24 小时时，`GitHub 精选` 仍然用 7 天；请求 14 天时，四个板块都用 14 天。
